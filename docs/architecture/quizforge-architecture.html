QuizForge is an AI agent that reads a Markdown README (a URL), writes a 5–8 question multiple-choice quiz, lets a user take it in a web app and computes a weighted score. It runs on AWS, is built with Terraform and deployed by GitHub Actions. Every quiz is traced and scored in Langfuse.

Architecture

Everything runs in one AWS region (us-east-2), in two zones, created by Terraform.

PieceWhat it doesWhy this choice
CloudFront + WAF → ALBThe only public entrance: HTTPS, a rate limit of 1000 requests per 5 minutes per IP, managed rules. The load balancer accepts CloudFront onlyNo custom domain was available, so the CloudFront address is the app address
web (Next.js, 2–6 tasks)The pages and a BFF: it keeps the login in an httpOnly cookie and calls the API with the tokenTokens never reach the browser's JavaScript
api (Fastify, 2–6 tasks)REST, JWT check, validation, quotas; it only enqueues the generation and answers at onceGenerating takes ~30 s and costs money, so it is asynchronous

scorer (1–2 tasks)Judges a quiz after it is saved: an LLM judge and fixed checksThe user does not wait for the judge
RDS PostgreSQLAll data, and the agent's checkpointsIdempotency and scoring need real constraints and transactions
CognitoUsers and login (code flow with PKCE), no sign-upStandard JWT, no passwords stored by us

Modelling choices that matter

ChoiceWhy
Options in their own table; is_correct on the optionA multi-answer question needs no special structure; the answer key is never sent to the browser before the submit
answer_selections instead of an arrayThe database refuses an option that does not exist, and a score is a plain join
Score per answer and final score, with a scoring_versionThe user sees why; old attempts keep the rule they were scored with
No users tableCognito is the source of truth; every query filters by its sub, and another user's id answers 404
The rules live in the databaseUnique idempotency keys, one active attempt per user and quiz, a monotonic revision per answer, SELECT … FOR UPDATE on submit, checks on ranges

The agent and the score

Before the model: how the README is prepared

StepWhat it doesWhy
1 · DownloadOnly github.com and raw.githubusercontent.com, https, the name resolved to public addresses only, redirects re-checked, 10 s, 512 KB, text content typesThe URL is user input: it must not reach internal addresses or huge files
2 · Normalize and cleanLine endings and blank lines normalised; text hidden as Base64, hex, ROT13 and similar is decoded and looked into (a hidden instruction rejects the document); invisible characters and HTML comments are removedWhat the model reads is what a person reads
3 · LanguageDetected on the prose only (code blocks, inline code, links and HTML are dropped first); only English, Portuguese and Spanish are acceptedThe quality gates and rules are built for these three
4 · ClassifierOptional DeBERTa model, English only, flags a likely injection and never blocksA second opinion for paraphrased attacks
5 · StoreThe cleaned text is saved once per content hash; the scorer later reads the same text backOne version of the document for generation and scoring
6 · Route and cutA short document goes whole (cut at 60,000 characters); a long one with at least 4 sections is split by headings (below)The model gets a size it can handle
7 · Build the promptThe rules are in the system prompt; the document goes inside <document> tags and is told to be data; a fake closing tag in the README is neutralised; the topic is one plain lineThe document cannot pose as an instruction
8 · Model-call guardStrict message schema, size caps, the document inspected again, output tokens capped, a budget of 16 callsA last check at the only door to the model

The graph

StepWhat happens
routeNo model call: a short document (up to ~4,500 tokens) goes single-shot; a long one with 4 or more sections goes section-map-reduce, so the questions cover the whole document
generate and checkThe model returns strict JSON (validated by zod, repaired up to 2 times). Fixed checks: every question must carry a literal quote from the document; a question whose quote cannot be found is dropped, never shown
critique and reviseA second pass finds weak or ambiguous questions and rewrites them, at most 2 rounds
saveQuestions and options are written in one transaction, then the quiz is ready
ControlValue
Budget per job16 model calls, 120,000 tokens, 5 minutes; kept in the database, so a redelivered message does not reset it
RetriesModel HTTP 3 retries · JSON repair 2 · critique 2 rounds · queue 3 receives, then the dead-letter queue and an alarm
Resume after a crashLangGraph checkpoints in Postgres: a restarted worker continues without repeating paid calls. They are deleted when the quiz is saved, and after 24 h at the latest
ModelsGenerator MiniMax-M2.7, judge MiniMax-M3 (a different model, to reduce self-preference); both through one OpenAI-compatible client

The score (no AI)

LevelFormulaStored in
One question4 × max(0, (hits − misses) / K), K = number of correct options (single answer: 4 or 0)answers.score
Weight of a question1.1^(position − 1): each later question weighs 10% moreanswers.weight
Final score (0 to 4)Σ(weight × score) / Σ(weight); percentage = score / 4attempts.final_score

Computed by the server from the stored answer key and selections (packages/core/src/scoring.ts), never from a number sent by the browser. The LLM judge grades the quality of the quiz, not the user's answers.

Guardrails in execution

What happens to every request, in order, and what kind of check each step is.

Deterministic rules (code)A model
Input (README and request)WAF, JWT, CSRF, strict schemas, quotas · host allow-list and public IPs only · hidden or encoded text, 49 keyword rules, language policy (en, pt, es; statistical, no model call) · the model-call guardOne ML model, optional: a DeBERTa classifier (protectai/deberta-v3-base-prompt-injection-v2, ONNX, English only) that flags a document, never blocks. Off in AWS, on in the local stack
The model callThe document is sent as data inside <document> tags; budget of 16 callsThe generation LLM itself is told never to obey the document. This is the only probabilistic defence
Output (the reply)Output rails (JSON only, no prompt leak, no script, no new link, no echoed attack), the zod schema, the literal-quote grounding, the answer key hidden until the submitNone. No model checks the reply for injection. The LLM judge scores quality after the quiz is saved and blocks nothing
Rules first, models second
Every rule is cheap, deterministic and tested, and a threat is stopped by the first layer that can see it. A model is used only where a rule cannot decide (a paraphrased injection), and only to flag. Measured honestly on a public dataset of 500 samples: the guard caught 28% of the English injections, the classifier 39%, both 47%, with no false positives in the English subset. So the model resisting, and the output rails, matter.

promptfoo: proving the guardrails

The tests behind the guardrails.

SuiteRunsModelTests
OfflineEvery pull requestA fake model with fixed answers: free and instant81: the whole attack corpus, language policy, bad topics, bad model replies, prompt safety rules
LiveA pull request that touches prompts or LLM code, every merge to main, every nightThe real MiniMax model, as the thing being tested21: does the real model follow an instruction hidden in a document, write something that is not a quiz, or leave its purpose?
QuestionAnswer
What is it?A test runner for prompts. It runs the real pipeline (guard, prompts, output rails) against one attack corpus (packages/core/src/attacks.ts, shared with the unit tests)
Is it a guardrail?No. It protects no user: it proves, before each deploy, that the guardrails above still work. A pull request that breaks one cannot merge
Where is a model used?Only as the system under test in the live suite. Every assertion is plain code (blocked, rejected language, accepted quiz, injected marker absent, on purpose); no model judges another model
Does it work?Checked by mutation: removing a rule from a prompt, or switching off the Base64 detector, turns the suite red

Trade-offs and next steps

What was decided on purpose, and what would change it.

TopicWhat we choseWhat would change it
Agent checkpointsIn Postgres, deleted when the quiz is saved and after 24 h at the latest: no extra serviceRedis or Valkey with a native TTL (about US$12 a month), only if the checkpoint writes show up in the database metrics
Address and TLSThe CloudFront address, TLS 1.0 and up, plain HTTP between CloudFront and the load balancer inside AWSA domain with an ACM certificate
AvailabilityOne NAT gateway and a single-zone databaseFlags exist for multi-zone, about +$50 a month
A distributed floodLimited by the WAF per IP and by autoscalingShield Advanced, or country and reputation rules
README sourcesAny public GitHub repository (host allow-list)Restrict to the catalog or to a list of owners
Guard coverageExplicit patterns; the rest relies on the model and the output railsA multilingual classifier, more keyword languages, red-team generated attacks
Evaluation size5 golden documents: small differences are noiseMore documents and repeated runs
